A custom image refers to an edition of **an image-based Linux distribution** tailored specifically to **meet the needs of a single individual or a select group of users**.

An image-based Linux distribution refers to a distribution where the entire system is **continuously delivered to users as a single, whole package, called an image**. This is as opposed to traditional Linux distributions, where every system package, including the kernel and drivers, **are installed and updated each separately by a package manager**. 

The techonology of image-based Linux has been pioneered by Fedora, specifically the so-called [atomic desktops](https://fedoraproject.org/atomic-desktops/) and [fedora-bootc](https://docs.fedoraproject.org/en-US/bootc/getting-started/), first with `rpm-ostree` and nowadays with bootc. **The [bootc](https://bootc.dev/) project enables ransactional, in-place operating system updates using [OCI container images](https://opencontainers.org/)** as the transport format. This allows us to leverage standard OCI container build techniques (like [Containerfiles](https://github.com/containers/common/blob/main/docs/Containerfile.5.md)) and infrastructure (like container registries built into Git forges, ex. [ghcr.io](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)).

This emerging technology has spawned development efforts such as:
- The [Universal Blue community](https://universal-blue.org/) who build [Bazzite](https://bazzite.gg/) among other custom images intended for different userbases.
  - Fun fact, BlueBuild was born as a small part of Universal Blue, before being spun out to be it's own thing!
- [Bootcrew](https://github.com/bootcrew/) who build proof-of-concept image-based editions of other non-Fedora distributions.

The lineage of image-based Linux distributions is related to and often confused with immutable distributions, butthe ease of modification of image-based Linux systems using OCI tooling or specialized tools such as BlueBuild proves that these systems are  **very much not immutable**, and are **usable & fun for tinkerers and nerds** as well. The read-only nature of system-level packages like the kernel, systemd, and drivers only serves to make your running systems **exceptionally stable**, since there is no way for the system to be broken by an incomplete update for example. The base system is rock-solid and not disturbed by userspace packages, which are handled by [Flatpak](https://flatpak.org/), [Brew](https://brew.sh/), [Mise](https://mise.jdx.dev/), or whatever tool is preferred.

## 1. Define your image

<div class="grid md:grid-cols-2">
<div class="m-4 p-3 px-4 border">
Our standardized [recipe format](/reference/recipe/) allows you to declare every part of your custom image in a **friendly** way, **designed for humans** (while being easily written programmatically as well).

We offer **full IDE-autocompletion** through JSONSchema anywhere where the YAML language server is available.

BlueBuild enforces a standard structure for repositories, so you always feel at home, even when helping someone else:
**one recipe file = one custom image**.

The recipe file defines the name of the image, the [base image](/learn/base-images/) to use, and the customization to add on top using [modules](/learn/modules/). Module configuration [can easily be shared](/how-to/multiple-files/) between recipe files, though.
</div>
<div class="m-4 h-128 overflow-y-scroll">
```yaml title="recipe.yml"
# yaml-language-server: $schema=https://schema.blue-build.org/recipe-v2.json
version: 2

metadata:
  name: weird-os
  description: This is my personal OS image.
  
base:
 image: ghcr.io/blue-build/base-images/fedora-silverblue:latest

modules:
  - type: files
    files:
      - source: system
        destination: /
      
  - type: dnf
    repos:
      copr:
        - atim/starship
        - monkeygold/nautilus-open-any-terminal
    install:
      packages:
        - micro
        - foot
        - starship
        - tailscale
        - android-tools
        - nautilus-open-any-terminal
  
  - type: systemd
    system:
      enabled:
        - tailscaled.service
  
  - type: gnome-extensions
    install:
      - Blur my Shell
      
  - type: fonts
    fonts:
      nerd-fonts:
        - FiraCode
        - JetBrainsMono
```

## 2. Build with BlueBuild

<div class="grid md:grid-cols-2">
<div class="m-4 p-3 px-4 border">
BlueBuild lets you **stop worrying about crafting pipelines or bespoke build scripts**. The [BlueBuild CLI](https://github.com/blue-build/cli) functions as a shared CI/CD pipeline, maintained by our community, and built in Rust instead of a flimsy scripting language (or god-forbid, GitHub Actions YAML).

The build system can be installed and used locally on any Linux system. It also runs comfortably on GitHub Actions, GitLab CI/CD, Forgejo Actions, or any other environment that can be used to build OCI container images with custom tools.

BlueBuild CLI doesn't only implement the process of turning your `recipe.yml` into a `Containerfile` and building it, it also handles other useful and potentially complicated steps such as validating the base image signature, building multiplatform images, and tagging, pushing and signing images. And this is all automagically handled in one command, `bluebuild build`!
